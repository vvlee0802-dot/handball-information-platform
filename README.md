# Handball Information Platform

手球信息与比赛分析平台。目前已完成 Epic 1、Epic 2、Epic 3、Epic 4，以及 Epic 5 的 AI 分析任务和候选事件复核管线。

用户可以通过赛事、比赛、球队、球员或场馆查找信息。主要页面的数据由 FastAPI 从 PostgreSQL 读取；具备权限的教练或分析师可以上传 MP4 录像、标注并确认比赛事件，再生成可预览和下载的视频片段。AI 已能生成可审核的进球候选，跨比赛泛化与更多事件类型仍属于后续开发范围。

2. 具备视频上传与标注权限的用户可以为处理完成的视频启动后台分析，接口立即返回任务编号和 queued 状态。
3. 后台使用 FFmpeg 对视频帧进行实际扫描，并持续把 running、处理阶段和进度写入 PostgreSQL；刷新或重新进入页面后仍可恢复显示。
4. 数据库使用部分唯一索引保证同一视频最多只有一个 queued 或 running 任务；重复提交直接返回已有任务及其编号。
5. 运行中的 AI 任务会阻止源视频删除；页面自动轮询活动任务，进入 completed 或 failed 后停止，并展示失败原因。

US5.1 只负责可靠的任务调度和视频扫描；候选进球、置信度、模型版本以及人工复核由下面的 US5.2 管线承接。

## US5.2 本版改动

1. 事件记录新增置信度、模型版本和分析任务来源字段，分析任务新增候选数量和本次运行的模型版本。
2. 建立独立的进球检测器接口；训练模型可以返回时间戳和置信度，任务服务负责校验范围、过滤非法结果并合并 3 秒内的重复候选。
3. 合法候选按视频时间写入现有事件表，统一标记为 `source=ai`、`status=draft`，不会在人工确认前进入正式统计。
4. 事件时间轴展示 AI 候选的置信度和模型版本，并复用已有的视频跳转、确认、修改、删除及片段导出能力。
5. 页面在 AI 任务结束后自动刷新事件；任务区域同步展示候选数量和模型版本。
6. 当人工已确认进球数与最终比分完全一致时，任务自动进入整场评估模式；AI 候选与人工进球在 ±8 秒内进行一对一匹配，不会向事件列表重复写入。
7. 评估结果持久化保存命中、漏检、误报、Precision、Recall、F1 和平均时间偏差，并直接显示在比赛详情页。
8. 对于尚未完整标注的新比赛，继续产生待人工审核的 AI 草稿；重新分析时会替换旧的未确认草稿，已确认事件不受影响。
9. 新增 AI 识别明细表，保留每条命中、误报和漏检的时间、置信度、匹配事件、时间偏差和训练审核结果。
10. 比赛详情页可按命中、误报、漏检筛选，并跳转到对应视频时间；人工确认的误报可加入下一版困难负样本。

当前代码已经完成第一版真实进球检测闭环：人工确认的进球标注用于生成正样本，远离进球时间的比赛画面用于生成等量负样本；VideoMAE 预训练编码器提取视频特征，小型线性分类器学习“进球 / 非进球”。整场分析时以 2 FPS 顺序读取视频，每 5 秒评估一个 13 秒窗口，并将连续命中的窗口合并为一个待人工确认的候选事件。

第一场比赛共形成 65 个进球和 65 个非进球样本，按比赛时间划分出 102 个训练样本和 28 个验证样本。第一版验证准确率、精确率、召回率和 F1 均为 78.6%（11 个进球命中、11 个非进球命中、3 个误报、3 个漏报）。训练和验证仍来自同一场比赛，因此该结果只证明原型链路可行，不能代表跨比赛泛化能力；下一步需要增加第二场完整标注比赛作为独立测试集。

整场 4813.685 秒录像的端到端评估更严格：模型生成 95 个候选，在 65 个真实进球中命中 36 个，漏检 29 个、误报 59 个，Precision 37.9%、Recall 55.4%、F1 45.0%，命中事件的平均时间偏差为 2.89 秒。该结果表明当前模型只能作为人工复核的早期候选器，不能作为自动统计的最终判定。

人工复核 59 个误报后，48 个有效困难负样本进入 V2，11 个包含真实进球、回放或其他不可靠标签的片段被排除。V2 共包含 178 个样本；按比赛时间隔离后，38 个困难负样本用于训练，最后 20% 时间段中的 10 个困难负样本只用于验证。在同一套 38 个 V2 验证样本上，V1 的 Precision、Recall、F1 分别为 50.0%、78.6%、61.1%，V2 分别为 71.4%、71.4%、71.4%；V2 将误报从 11 个降到 4 个，同时漏报从 3 个增加到 4 个。由于数据仍来自同一场比赛，V2 只能作为当前本地候选模型，仍需第二场完整标注比赛验证泛化能力。

V2 整场扫描同时统一了训练和推理的画面预处理：保持原始宽高比并居中裁剪，不再使用会产生上下黑边的缩放方式。修复后的整场结果为 106 个候选、49 个命中、57 个误报和 16 个漏报，Precision 46.2%、Recall 75.4%、F1 57.3%，平均时间误差 2.216 秒。相比 V1，命中增加 13 个、漏报减少 13 个、误报减少 2 个，F1 从 45.0% 提高到 57.3%；当前结果仍属于需要人工复核的候选器，而不是正式比赛统计的自动判定。

## US5.4 本版改动

1. 比赛详情页固定展示 AI 分析支持边界，说明当前模型主要适用于清晰、完整、接近训练样本的横向转播画面。
2. 页面明确提示侧后方机位、严重遮挡、低清晰度、回放镜头和不同转播风格可能降低识别效果。
3. 置信度低于 65% 的候选会显示“低置信度，必须人工确认”，且所有 AI 候选仍保持草稿状态，不会自动进入正式比赛统计。
4. 分析完成但没有生成候选时，页面会提示“未发现候选不代表比赛没有进球”，引导用户继续人工检查或人工标注。
5. 在 V2 验证特征上复核 0.20 至 0.80 的候选阈值；当前 0.50 阈值的 Precision、Recall 和 F1 均为 71.4%，F1 优于相邻候选，因此暂不为阈值问题训练 V3。
6. 新增前端边界判断单元测试，并在真实比赛详情页完成提示文案的页面级检查。

### 本地进球模型训练

数据集、特征缓存和模型产物均保留在本机并由 Git 忽略，原始录像不会被复制进仓库：

```bash
cd backend
source .venv/bin/activate
python -m pip install -r requirements-ml.txt

# 1. 从人工进球和已审核误报生成独立的 V2 清单
python -m app.scripts.build_goal_dataset \
  --match-id 1 \
  --output-dir datasets/goal_detection/v2

# 2. 从原始录像切出 13 秒轻量训练片段
python -m app.scripts.materialize_goal_dataset \
  --manifest datasets/goal_detection/v2/match-1/manifest.jsonl

# 3. 提取 VideoMAE 特征并训练分类头
python -m app.scripts.train_goal_model \
  --manifest datasets/goal_detection/v2/match-1/manifest.jsonl \
  --model-version goal-detector-v2 \
  --local-files-only

# 4. 在完全相同的 V2 验证集上公平比较 V1 和 V2
python -m app.scripts.compare_goal_models \
  --manifest datasets/goal_detection/v2/match-1/manifest.jsonl \
  --model-dir model_artifacts/goal_detector/v1 \
  --model-dir model_artifacts/goal_detector/v2 \
  --output datasets/goal_detection/v2/match-1/model-comparison.json
```

模型根据 `--model-version` 保存到独立目录，V1 和 V2 可以同时保留；FastAPI 当前默认加载 `backend/model_artifacts/goal_detector/v2`，也可以通过 `GOAL_MODEL_DIR` 回退到其他版本。如产物不存在，则安全退回 US5.1 的帧扫描并返回 0 条候选，不会伪造结果。当前使用的 `MCG-NJU/videomae-small-finetuned-kinetics` 权重为 CC-BY-NC-4.0，仅适合当前非商业学习与作品集场景，商业部署前必须替换为许可合适的模型。

## 核心数据模型

- `Competition`：赛事
- `Team`：球队
- `Player`：球员，通过 `team_id` 关联球队
- `Venue`：场馆
- `Match`：比赛，通过外键关联赛事、主队、客队和场馆
- `User`：注册用户，只保存密码哈希，不保存明文密码
- `AuthSession`：服务端会话，只保存随机会话令牌的摘要
- `UserPermission`：用户在角色默认权限之外获得的可配置权限
- `Video`：比赛录像元数据，通过 `match_id` 关联比赛，记录类型、时长、处理与删除状态；文件本体保存在可配置存储目录
- `VideoUploadSession`：可恢复上传会话，记录文件指纹、分片方案、所属用户和上传状态
- `VideoUploadPart`：已成功接收的分片元数据，用于续传、去重和完整性校验
- `Event`：人工或 AI 比赛事件，通过 `match_id` 和 `video_id` 关联比赛录像；AI 候选额外记录置信度、模型版本和分析任务来源
- `ClipExport`：事件片段导出任务，记录处理状态、输出文件和失败原因
- `ClipExportEvent`：导出任务与已确认事件的有序关联，用于生成单事件片段或多事件合并视频
- `AnalysisTask`：视频 AI 分析任务，记录任务编号、运行状态、处理阶段、进度和失败原因

所有实体均使用稳定 ID 建立关系，避免使用显示名称作为数据关联依据。

## 本地运行

### 1. 配置环境变量并启动 PostgreSQL

```bash
cp .env.example .env
docker compose up -d
```

### 2. 启动后端

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m alembic upgrade head
python -m app.scripts.create_user --email admin@example.com --name "系统管理员"
python -m uvicorn app.main:app --reload --port 8000
```

这条命令只用于创建第一个系统管理员，终端会要求输入并确认密码。之后可以登录网页，在“用户管理”页面创建其他账号，不需要每次使用终端。

健康检查：`http://127.0.0.1:8000/api/health`

API 文档：`http://127.0.0.1:8000/docs`

### 3. 启动前端

```bash
cd frontend
npm install
npm run dev
```

## 当前范围说明

当前版本已经支持在比赛详情页分片上传 MP4 录像、恢复中断上传、管理多条视频记录，并从已确认事件生成可预览和下载的 MP4 片段。

目前视频本体、临时分片和导出片段保存在 `VIDEO_UPLOAD_DIR` 指向的本地目录；切换为云端对象存储、独立任务队列和 AI 分析仍属于后续 US 与 Epic。
